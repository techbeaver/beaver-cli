# 0012. Install script first; package managers are tier 2; no .pkg or .msi

## Status

Accepted.

## Context

The question was whether a package manager is compulsory, or whether an installer per platform and
architecture would do.

Neither, and one detail decides it. **A downloaded binary is not on `PATH`.** Someone who downloads
`beaver-darwin-arm64` gets a file in `~/Downloads` that their shell cannot find, and on macOS it also
carries a quarantine attribute that refuses to execute until cleared. The work a package manager does
is not fetching the file, it is placing it on `PATH` and making it runnable. A download page leaves
the user doing exactly the part that fails.

Graphical installers solve it, but a `.pkg` and an `.msi` are two more signed artefacts, two more
build paths and two more things to test, for a population that mostly lives in a terminal already.

## Decision

**Tier 1, the documented path:** a shell script fetched over HTTPS from `techbeaver.io/install.sh`.
It detects platform and architecture, downloads the matching release asset, verifies its checksum,
clears the macOS quarantine attribute, and places the binary on `PATH`. Windows gets the PowerShell
equivalent.

**Tier 2, if customers ask:** a Homebrew tap and a Scoop bucket. Both are generated by the release
tooling, so they cost a configuration block rather than a pipeline.

**Not built:** `.pkg`, `.msi`, distribution packages, and any form of self-update. The version check
reports that a newer release exists and never downloads or executes anything. A CLI that updates
itself is a remote code execution path into every machine that installed it.

macOS builds are notarised with Apple, since the account already exists. That removes the Gatekeeper
warning for anyone who does download the binary directly, and it does not change this decision,
because a notarised binary in `~/Downloads` is still not on `PATH`.

## Consequences

`curl ... | sh` is a pattern some customers refuse on principle, correctly. The release page therefore
documents the manual path too: download, verify the checksum and the signature, `chmod +x`, move it
onto `PATH`. The script is a convenience over a documented process, never the only way in.

The script is served from the marketing site rather than a dedicated hostname, so it needs no new DNS
record and no new origin configuration. That matters: a hostname whose origin was never configured is
precisely the failure that took a service down during this project.

Releases are signed and carry provenance. The risk a published binary creates is not us shipping
something bad, it is somebody else shipping something bad under our name, and a signature the customer
can verify is the only defence they have.
